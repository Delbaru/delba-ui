# Проверка UI-кита

Применяй при проверке по задаче без отдельного вызова. Прочитай
[принципы](../../../docs/specs/architecture/principles.md), применимые темы из
[карты спецификаций](../../../docs/specs/README.md) и [приёмку](../../../docs/specs/verification/acceptance.md).
Сопоставь критерии предметного изменения с выполненными проверками; базовый
договор не подтверждает автоматически соответствие всех существующих компонентов.

Пути ниже — от корня UI-репозитория. Полный состав проверок —
[checks](../../../docs/checks.md) и [tools/check/index.mjs](../../../tools/check/index.mjs).

## Гейты по диффу

- Только docs/skills/входы: `node tools/agent-docs.mjs check .`;
  продуктовые типы, browser/SSR и build не требуются.
- Изменение проверочного инструмента: выполни его на действительных источниках
  и проверь существенные режимы отказа отдельно от приложения.
- Код кита в отдельном клоне: `npm run check` при установленных зависимостях.
- Кит в потребителе: `pnpm exec delba-ui test` из каталога приложения с ui.config.
  Корневую обёртку запуска используй только после проверки scripts и инструкции
  конкретного потребителя; наличие `ui:test` или включение gate в `verify` не предполагается.
  Scan roots относительны рабочему каталогу потребителя: один `--config` с чужим путём
  не меняет корень. Не запускай project generation из каталога кита.
  Успешный gate без нового диффа повторять не нужно.
- Меняется интеграция/импорт/ассет: production build потребителя.
  После глобальных типов — проверка с `--incremental false`.
- Новые layout-значения: генерация и проверка полученных классов.

## CI потребителя

Деплой ждёт агрегатный gate после проверки source fingerprint, `library` и всех
четырёх browser/SSR shards. Переиспользуется только подтверждённый успешный результат
для того же кита, Node, зависимостей, конфигурации и сгенерированных стилей; без fallback
ключей. Пропуск, ошибка и отмена обязательной части запрещают деплой. Project checks
выполняются на каждом изменении потребителя. Реализация и состав частей —
[checks](../../../docs/checks.md); не заводи облегчающий обход в workflow проекта.

## Контракт

Примени [обязательный чеклист читаемости](../../../docs/specs/architecture/readable-api.md).
Для глобального аудита потребуй карту покрытия всех областей и явно непрочитанное.
Не называй предложенные exports существующими, а чтение кода — браузерной приёмкой.

Сверь публичные React-экспорты с [каталогом](../../../docs/specs/ui/components/README.md):
у затронутого компонента есть своя страница, её props/defaults и пример соответствуют
коду. При смене договора проверь TSX-пример по типам установленного API; для полного
каталога проверь также отсутствие пропущенных/непубличных имён. Типы и ссылки не
подтверждают runtime — поведенческую приёмку веди отдельно.

Проверь отсутствие внешних импортов, токены стартовой темы, CSS layers,
responsive/null, TS, публичные JSDoc/exports, DOM ref и callback cleanup.
Сохрани controlled-состояние, композицию событий, SSR, фокус, reduced motion
и публичную совместимость. Ломающий API требует явной миграции.
Для ref-наблюдателя, принимающего object ref и callback target, проверь оба входа,
первое наблюдение после mount, замену target и cleanup в браузере.
Для потребительского проекта проверь форму публичных D-компонентов в
`src/shared/ui` и `src/cms/ui` через `pnpm exec delba-ui test --suite project`;
проверка запускается из корня приложения и не задаёт файловую форму внутренностям DelbaUI.
При интеграции проверь переиспользование готового проектного D\*-компонента,
если он задаёт нужное оформление; нейтральные layout-примитивы не требуют обёрток.
Regression-тест должен воспроизводить установленный баг тем же путём, что живой код.

## Браузер

Проверяй владельца fixture, а не только HTTP 200: штатный global setup сверяет checkout.
Не отключай эту проверку ради reuseExistingServer; при конфликте используй UI_BROWSER_PORT.
Для первого показа обязательны холодный кеш, задержка fonts/JS и отключённый JS;
SVG проверяй в SSR, а bootstrap — также с ошибкой и бесконечным ожиданием шрифта.
В потребителе выполни `delba-ui startup --url <production-URL> --font "selector=Family"`.
Фактический custom font проверяется через CDP: preload и computed font-family
не доказывают применение нужного файла. Учитывай preload также в HTTP Link.

Проверяй экран, где компонент действительно используется. Сначала обнаружь доступные tools:
Chrome DevTools MCP для CSS/console/network/trace, DevTools или Playwright для реальных жестов.
Ref/uid бери из текущего снимка; snapshot подтверждает действия, screenshot — вид.
Ввод, Tab/Enter/Space/Escape, hover, быстрый разворот и portals проверяются отдельно.
Не подменяй ввод присваиванием DOM.value и не выдавай unit-тест за визуальную проверку.
Motion проверяется в начале, в ходе и после завершения; для динамического контейнера
пройди пустой, один, несколько элементов и обратный путь. Фиксируй размеры поверхности,
а для счётчика — видимое значение и видимость предков в одни моменты времени.
Motion дополнительно проверяется с reduced motion и unmount; измерения —
[ui-performance](../ui-performance/SKILL.md).
Короткие промежуточные состояния связанных узлов записывай одним наблюдателем
в браузере до запуска движения: последовательный polling может пропустить их.

Для native scrollbar отключай headless-флаг `--hide-scrollbars` только в его
сценариях: computed CSS не доказывает отрисовку и native drag. Проверяй реальное
перетаскивание за пределы viewport, промежуточную окраску и screenshot.

Обнови контракт в docs и реальный новый урок в lessons, сохраняя адреса прежних.
Доклад различает выполненные гейты, просмотренные состояния и существенное непроверенное.

При reuse fixture из Dev Launcher передай её фактический порт через UI_BROWSER_PORT;
иначе Playwright вычислит другой порт и запустит вторую копию. Это не разрешение
запускать браузер, когда владелец явно отложил браузерную приёмку.

## Дополнение: стили, композиция и переиспользование

- [ ] У каждой визуальной части собственный SCSS-модуль и именованный класс
  на существующем корне; нет импорта SCSS родителя/соседа и лишнего DOM ради класса.
- [ ] Пустой корневой селектор проверен через сборку и реальный DOM: CSS Modules
  не гарантирует сохранение пустого правила. Нет фиктивных деклараций.
- [ ] Выделенные подкомпоненты имеют именованные папки; фрагменты JSX не дробятся.
- [ ] Интерактивная панель возле якоря (например, InputCalendar или Select) использует
  Dropdown через подходящий контракт и не копирует portal/position/dismiss. Tooltip
  и Modal сохраняют собственные семантику и lifecycle, переиспользуя нужное общее ядро.
- [ ] InputCalendar сохраняет собственные правила выбора/валидации даты;
  Dropdown владеет поверхностью, позиционированием, порталами и dismiss.
- [ ] На этапе DelbaUI изменения принадлежат её репозиторию. Обновление сайта, CMS
  и их ссылок выполняется отдельным согласованным этапом интеграции. Playwright выполняется после завершения
  всех групп изменений, затем исправления и повтор затронутых сценариев.

## Размещение тестов

Unit-тесты и статические проверки типов находятся в `tests/` у владельца:
`Name/tests/Name.model.test.ts`, `core/base/tests/focus.test.ts`.
`*.type-test.ts` и `*.typecheck.tsx` также относятся к тестам и не лежат
рядом с runtime-файлами. Общие проверки инструментов — в `tools/tests/`
или `tools/<module>/tests/`. Браузерные `*.spec.ts` — в
`tools/browser/tests/`; fixtures, setup и Playwright/Vite config остаются
в корне браузерного harness. Штатный unit-gate проверяет это правило через
`tools/check/test-placement.mjs`. Перенос сохраняет набор сценариев,
исправляет относительные импорты и пути `import.meta.url`; удаление теста
ради чистого дерева недопустимо.
