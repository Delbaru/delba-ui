# Компонент библиотеки components

Этот скилл — **вход в справочник, а не его копия.** Навигатор — [`docs/Library.md`](../../../docs/Library.md).

Применяй по задаче без отдельного вызова. До изменения прочитай
[принципы](../../../docs/specs/architecture/principles.md) и затронутые темы:
[ядро](../../../docs/specs/architecture/core.md), [API](../../../docs/specs/architecture/api.md)
или [компоненты](../../../docs/specs/ui/components.md). Для нового договора следуй
[карте спецификаций](../../../docs/specs/README.md); при сдаче сопоставь критерии
с [приёмкой](../../../docs/specs/verification/acceptance.md). Не копируй справочник в спецификацию.
При интеграции экрана предпочитай готовые проектные D\*-компоненты с его скинами,
размерами и пресетами. Нейтральная раскладка остаётся доступна напрямую; не создавай
обёртку ради префикса. До изменения/использования найди отдельную страницу в
[каталоге компонентов](../../../docs/specs/ui/components/README.md). Обновляй её
договор, самостоятельный пример и приёмку вместе с API; новый публичный компонент
получает страницу и строку оглавления в той же задаче. JSDoc целиком не копируй.

> Библиотеку едят несколько проектов, каждый на своём коммите. Правка здесь приезжает ко всем,
> кто обновится. Здесь **требования, а не рекомендации.**

В проектных корнях `src/shared/ui` и `src/cms/ui` публичный `DName/` следует
анатомии из [authoring](../../../docs/authoring.md). Это не шаблон для папок
примитивов DelbaUI или их внутренних помощников.

Формат исходников кита задаёт его собственная .prettierrc. Настройки потребителя
не должны менять результат библиотечной архитектурной проверки.

## 2. PRE — до первой строки кода

До проектирования и перед показом пройди обязательный чеклист
[читаемого API](../../../docs/specs/architecture/readable-api.md). Один механизм,
однократная настройка и понятный потребитель проверяются вместе с внутренним
путём до ядра; новый namespace не оправдывает перенос прежней сложности.
При выполнении согласованного рефакторинга Input сверяй отдельный чеклист
[компонента](../../../docs/specs/ui/components/Input.md). Короткий Input не
принимается с прежней солянкой внутри useInput; режимы не вызывают hooks динамически.
Согласованную композицию не заменяй другой схемой без обсуждения. Проверь отдельно
модель, события, режимы, валидацию, оформление и представление; показывай целые
существенные внутренние файлы. Проверяй готовые возможности примитива до новой
обёртки/состояния: Text.collapse сам удерживает текст при закрытии; FieldFeedback
не копирует этот lifecycle. Для строки с портальными потомками проверяй
currentTarget.contains(target) перед переносом фокуса: React bubbling не доказывает
принадлежность DOM. Владелец утвердил новый эталон Input:
единый Field engine, чистые политики режимов и согласованное дерево. Input и
Calendar служат ориентиром. Объём изменения потребителей определяется текущим
поручением владельца; спецификация не заменяет разрешение обновить другой репозиторий.

Определи до изменения; в плане назови решения, существенные для задачи:

1. **Место.** Это библиотека (форма и поведение) или проект (продукт, скины, словари)?
   Бизнес-существительное в имени — значит проект.
2. **Инвентарь ядра.** Открыт ли [`docs/core.md`](../../../docs/core.md)? Чего из нужного там ещё нет?
3. **Договор.** Какие токены проекта понадобятся и все ли они уже в `theme/tokens.default.scss`?

## 3. Красные линии — нарушение любой = переделка

1. **Ни одного импорта наружу папки.** Сторож `tools/check-boundary.mjs`.
2. **Цвет, шрифт, длительность, тень — токеном проекта.** Новый токен — сразу в стартовую тему.
3. **Респонсив — кортеж `[desktop, mobile, tablet]`; `null` = пропуск брейкпоинта.**
   «Как на desktop» — значением. Внутри библиотеки нормализуй `resolveResponsive`.
4. **Строгий TypeScript: без `any`, `!`, `@ts-ignore`, `eslint-disable`.** Индексация массива даёт
   `T | undefined` — это проверяется, а не утверждается.
5. **Пропы коробки — из `src/core/layout/box.ts`**, а не свои копии отступов и размеров.
6. **`ref` — обычный проп (`WithRef`), склейка — `useMergedRefs`.** `forwardRef` не используем.
7. **Каждый визуальный компонент и подкомпонент имеет собственный Name.module.scss и styles.Name на существующем корне.** SCSS родителя/соседа не импортируется; общие ui-* механизмы сохраняются. Не создавай лишний DOM ради класса. Не добавляй literal Name рядом с module-классом: пустой модуль может не выдать DOM-класс, это не исправляют фиктивным CSS.
8. **Слои: покой в `ui.components`, пропы в `ui.utilities`, состояния в `ui.states`.**
9. **SCSS — только непропсовое** (overflow, transform, transition, z-index, opacity,
   псевдоэлементы, селекторы состояний). Отступ, размер, радиус, фон — пропом.
10. **`@media` ради размера — ошибка**: это кортеж. Законные медиазапросы берутся из `MEDIA_QUERY`
    или миксинов ядра.
11. **Повторяющийся рецепт SCSS — миксин в `src/core/_mixins.scss`**, а не копия.
12. **`z-index` — токен `--z-*`**, если это этаж приложения, а не порядок двух соседних узлов.
13. **Движение уважает `prefers-reduced-motion`; страховка — `MOTION_END_BUFFER_MS`.**
14. **JSDoc у каждого публичного пропа.**
    Общие настраиваемые defaults поведения и движения принадлежат типизированному ui.config
    и единой генерации CSS/runtime/SSR; компонент задаёт только явное намерение экземпляра.
15. **Публичное только добавляют.** Ломающая правка — коммит с пометкой `BREAKING:` и объяснением,
    как перейти. Неиспользуемый, но рабочий компонент НЕ удаляют: он живёт ради других проектов.

Декоративная рамка не должна забирать псевдоэлементы потребителя или клиповать его
контент. Для градиента проверь прозрачный центр, радиусы, responsive и совместимость
с hover/focus/ссылкой; повторяемую механику держи в общем компоненте (GradientBorder).

При упрощении API сокращай общую повторяемую механику, сохраняя видимыми решения
потребителя. Факты и boolean (`useScroll().y`, `down(32)`) позволяют обычному React
выбирать state; ядро не знает проектных compact/hide и не задаёт их стили.
Не заменяй if/useState системой команд, render-обёрткой или ручкой set стилей без
самостоятельной задачи. Пресет — готовый набор настроек; размер/геометрия — size/layout.
Сохранённые DOM/ref/events/SSR/reduced motion важнее уменьшения числа строк.
DOM-конструкторы observer и проверки instanceof бери из ownerDocument.defaultView:
порталы, iframe и JSDOM могут принадлежать другому realm без копий на globalThis.
Если hook принимает object ref и callback target, сохраняй оба варианта; object-ref
тест включает начальное наблюдение и замену DOM-узла после commit.
Маскированное поле проверяй нативными Backspace/Delete, выделением и paste:
правильные итоговые цифры не доказывают сохранённую каретку. Ёмкость формата
не должна зависеть от декоративного образца подсказки.
Составное поле сохраняет нативный договор: uncontrolled checked/reset, отменённый reset,
form= и readonly/disabled на каждом пути записи. Подписка на DOM переподключается при
замене ref target; события дополняются composeInteractionHandlers, не spread-перекрытием.
Проверяй переходы во время действия: disabled убирает активные tab-stop/actions,
loading закрывает недоступный список, новый controlled-источник отменяет старый async
результат через существующего владельца операции.
Для правки API проследи полный путь реального потребителя: настройка → генерация/
адаптер → ядро → CSS/SSR/клиент. На каждом переходе проверь направление импорта,
единственного владельца значения/состояния и фактическое использование настройки.
При передаче поведения провайдеру проверь сохранение публичных опций на обоих
путях: с провайдером и без него; успешный тест одной ветки не подтверждает другую.
Потребитель выбирает намерение через публичный API с автодополнением; формулы и
lifecycle остаются в ядре. Не прячь проектные значения за fallback кита, синонимом
или обёрткой без ответственности. Проверяй читаемость всего компонента и реальной
цепочки потребитель → API → hook/helper → DOM/runtime, не только пары строк вокруг
вызова; проследи настройки до фактического эффекта. Разворачивай сложные объекты.
Короткий внешний API не делает длинную внутреннюю последовательность понятной.

Перед новым hook, компонентом, callback или реестром сначала найди текущего владельца
поведения и уже существующие механизмы. Удаляй подтверждённое дублирование. Выделяй
ответственность, только если граница уменьшает связность и имеет собственные причины
изменения; если для неё приходится протягивать множество refs/callbacks, оставь связанную
логику вместе и сделай последовательность шагов ясной. Не вводи слой, который только
переименовывает один вызов, и не поддерживай параллельные определения одного реестра.
Команды должны быть типизированными, предметно названы и документированы JSDoc.
UI-кит не принимает God-object проекта и не импортирует сайт или CMS: потребитель
передаёт только нужные значения через публичный контракт.

Не используй компактный `ProductGallery` сайта как образец простой композиции: оценивай
весь его путь, включая controller, регистрацию видео, миниатюры и уже существующую
автопаузу карусели. Отдельный `VideoTimeline` из предыдущего аудита — отозванная идея,
а не целевой компонент; сначала докажи, что извлечение сокращает связность, а не только
переносит refs и callbacks.

## 4. Сдача

Приёмка — `прочитать .agents/skills/ui-verify/SKILL.md`, не на глаз.

Урок после задачи обязателен и не ждёт просьбы: ошибка — в `docs/lessons/*.md` («симптом → причина →
лечение»), новое правило — в `docs/authoring.md`, новая общая вещь — в `docs/core.md`.

При смене режима или binding проверяй восстановление настоящего uncontrolled DOM,
а не только сохранённого draft. JSDoc описывает краткий договор, defaults и эффекты;
история продуктового решения хранится в документации, не в пропсе.

Крупный самостоятельный подкомпонент располагай в Name/Name.tsx внутри владельца;
собственные SCSS/config живут рядом, общую папку parts не создавай. Малый фрагмент
на 1–10 строк обычно остаётся в JSX; отдельный компонент требует своей обязанности.


Новый и рефакторируемый UI использует только объектный animate с явными when/effect.
Удаляй animation/transitionKey и строковые/tuple-вызовы в мигрируемом сценарии;
не добавляй совместимые алиасы, fallback или второй движок. inView/load/change
выбираются по событию, не по внешнему сходству. Проверь внутренние вызовы до ядра.
Для закреплённой версии кита сначала проверь поддержку API и согласованное обновление;
отсутствие API не оправдывает скрытый возврат к legacy.

При выделении визуальной части используй Name/Name.tsx и Name/Name.module.scss.
Проверяй экспорт пустого корневого селектора фактической сборкой; не вводи фиктивные
декларации. Если селектор удаляется, сохраняй узнаваемый DOM-маркер общим механизмом.

## Размещение тестов

Unit-тесты и статические проверки типов находятся в `tests/` у владельца:
`Name/tests/Name.model.test.ts`, `core/base/tests/focus.test.ts`.
`*.type-test.ts` и `*.typecheck.tsx` также относятся к тестам и не лежат
рядом с runtime-файлами. Общие проверки инструментов — в `tools/tests/`
или `tools/<module>/tests/`. Браузерные `*.spec.ts` — в
`tools/browser/tests/`; fixtures, setup и Playwright/Vite config остаются
в корне браузерного harness. Штатный unit-gate проверяет это правило через
`tools/check/test-placement.mjs`. Перенос сохраняет набор сценариев,
исправляет относительные импорты и пути `import.meta.url`; удаление теста
ради чистого дерева недопустимо.

Для ресурса со static import разрешай единый адрес до optimization, lightbox и
source identity, включая Next `{ default: image }`. Асинхронная готовность слоёв
принимает только событие актуального identity; поздний load уходящего кадра не
меняет состояние нового. Проверяй реальный SSR и жизненный цикл смены, а не только decoder.
Для art direction проверяй фактический currentSrc: корректные media/srcset в DOM
не доказывают выбор. Кодируй whitespace только в одиночном fallback URL, сохраняя
дескрипторы готового multi-candidate srcSet.

Действия поля проверяй также внутри внешнего native label: click по padding
действия не должен выполнять default activation связанного input. Отмена mousedown
не отменяет click default; зона действий имеет одного владельца этого поведения.
