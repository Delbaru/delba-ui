# Компоненты и состояния

Статус: базовый договор. Область: примитивы, составные контролы и их оформление.

Подробный авторинг — [authoring](../../authoring.md), готовая механика —
[core](../../core.md), проектные ограничения — [rules](../../rules.md).
Кит предоставляет форму и поведение; конкретная тема, скины, тексты и роли экрана
принадлежат потребителю. У каждого публичного React-компонента есть отдельная
страница в [каталоге компонентов](components/README.md). Этот документ задаёт общие
правила; конкретное применение и примеры читай на странице компонента.

## Примитивы и проектные компоненты

Примитивы DelbaUI — детали конструктора. На пользовательских экранах потребителя
предпочитай его готовые D*-компоненты: они закрепляют скины, размеры и пресеты,
чтобы один и тот же выбор оформления не повторялся в каждом месте.
Нейтральные `Box`, `Flex`, `Grid` и другая общая механика могут использоваться напрямую.
Не нужна отдельная D*-обёртка для каждого примитива; префикс сам по себе ничего не улучшает.
Если готового проектного компонента нет, оцени повторяемость и ответственность,
а не переименовывай примитив вслепую. Механика остаётся в ките, продуктовые скины — у потребителя.

Например, проектный `DButton` может закрепить варианты оформления поверх публичного
`Button`, сохранив его ссылку, события, ref и движение. Он живёт в приложении;
библиотека не импортирует его и не содержит фирменные значения проекта.
Подключение и движок скинов описаны в [README](../../../README.md).

## Краткая карточка компонента

У каждой страницы один предмет: **назначение → когда использовать → основной API →
самостоятельный пример → ограничения/состояния → критерии приёмки**. Подробный JSDoc
и внутреннюю реализацию связывай ссылками. При изменении компонента одновременно
обновляй его страницу и проверяй пример; новый публичный экспорт добавляй в оглавление.
Внутреннему помощнику отдельная потребительская страница не нужна.
У потребителя карточки D\*-компонентов принадлежат его документации.
Текущая карта кита — [Library](../../Library.md), публичный состав —
[exports](../../../src/index.ts), договор авторинга — [authoring](../../authoring.md).

Читаемость относится и к цепочке внутренних обязанностей: компонент, hook, обработчик,
парсер и форматтер должны называть действия и сохранять порядок решений видимым.
Разделяй по реальным причинам изменения; не дроби последовательность на файлы ради
коротких компонентов и не добавляй обёртки, которые только переименовывают вызов.

## Состояния и оформление

Для затронутого поведения опиши применимые состояния: исходное, открытое/закрытое,
disabled/error/loading, ввод, фокус и завершение действия. Не добавляй состояния,
которых у компонента нет. Сохраняй семантический DOM, доступное имя, клавиатуру,
стабильный ref и согласованность SSR/первого клиентского кадра.

Layout использует общие props и responsive-нормализацию; значения темы принадлежат
потребителю. CSS-слои разделяют покой, утилиты props и состояния; повторяемая
механика стилей имеет общего владельца. Проверяй не только внешний вид в покое,
но и реальный сценарий в приложении по [приёмке](../verification/acceptance.md).
Переходы описаны в [движении](motion.md).

Responsive-видимость имеет один вход: `hide={[desktop, mobile, tablet]}`,
где true скрывает, false/null сохраняют обычное отображение. Старые
`data-hide-mobile`, `data-hide-tablet`, `data-hide-pc` и `data-hide-desktop`
удаляются вместе с правилами тем и переносом потребителей. Полный префикс
`data-hide-*` не перенаправляется на корень; отдельный `data-hide-scrollbar`
сохраняется как независимая механика. При обновлении темы потребителя проверь
его закреплённый пакет: старый ChoiceButtons может ещё выдавать legacy-атрибуты.
