# Приёмка спецификации

Статус: базовый договор. Область: подтверждение результата изменения DelbaUI.

Команды и состав проверок принадлежат [checks](../../checks.md) и
[ui-verify](../../../.agents/skills/ui-verify/SKILL.md). Выбирай проверки по diff:
изменение только документов не требует продуктовой сборки или браузерных тестов.

Перед сдачей сопоставь каждый критерий предметной спецификации с результатом:
выполнен, не выполнен или не проверен, с причиной. Наличие описанного договора
не доказывает соответствие существующего кода и всех потребителей.

Перед проектированием и показом примени [чеклист читаемости](../architecture/readable-api.md).
Для полного аудита нужна карта всех областей с полным/частичным чтением и пробелами;
выбранные примеры не доказывают проверку всей библиотеки. Аудит не означает
разрешение немедленно реализовать предложенный API.

Для изменения кода проверь применимые границы, типы/exports, договор темы,
состояние и события, DOM/ref, SSR, доступность и совместимость. Браузерный
результат подтверждается в реальном потребителе; unit-тест не заменяет просмотр.
Изменение движения требует промежуточных фаз, отмены и reduced motion;
оптимизация — одинакового сценария и условий замера до/после.
Регрессия должна идти тем же путём, что и публичный контракт: для наблюдателя
с ref проверь первый mount и замену target, для HTML-парсера — реальные вложенные
блоки в DOM, а не только искусственно собранный результат helper.

Для docs/skills проверь маршруты из AGENTS, YAML и относительные ссылки,
включая новые спецификации. `node tools/agent-docs.mjs check .` проверяет входы
и навыки; новые файлы в `docs/specs` дополнительно проверь на существование целей
ссылок, поскольку общий инструмент не обходит этот каталог целиком.

Для рефакторинга оцени целые затронутые компоненты и реальные цепочки потребителей,
а не только короткие вызовы или выбранные строки. Найди существующие hooks, controllers,
helpers и автоматические реакции до добавления новых. Подтверждённое дублирование
должно исчезнуть; новая граница должна уменьшать связность без лишнего переноса refs,
callbacks или состояния. Реестры и перечни имеют одного владельца и источник определения.
Проверь, что библиотечный API принимает минимальные типизированные значения и команды,
а не объект продукта или CMS.

Сверь итоговый компонент с согласованным примером композиции, а не только с
общими принципами. Изменение интерфейсов частей должно быть отдельно объяснено
и согласовано. Проверь модель, события, режимы, валидацию, оформление и
представление по полным реализациям: непрозрачный объект и перенос старой логики
в hook не проходят архитектурную приёмку. Для Input источник эталона — его
[страница](../ui/components/Input.md); отмеченные там открытые решения не
считаются готовой реализацией.

Для [каталога компонентов](../ui/components/README.md) сравни набор страниц с
React-компонентами всех source-backed package-входов, включая `src/index.ts`,
`@delba/ui/carousel`, providers и составные части. Полноту страниц и строк каталога
проверяет штатный unit-тест `component-catalog.test.ts`.
TSX-примеры проверяй по реальному API со строгой типизацией и необходимыми peer/dependencies,
без подмены отсутствующего пакета декларацией `any`. Проверка примеров не должна
создавать демонстрационные компоненты в runtime. Отдельно сверяй текстовые обещания
props/defaults с исходником: успешный простой пример не обнаруживает ошибку в описании
неиспользованного пропса. Типизация не подтверждает доступность в браузере.

В результате перечисли фактически выполненные проверки и существенные ограничения.
Обнови подробный договор, если изменился API; подтверждённую новую причину ошибки
сохрани в соответствующем lessons. Разовые логи и отчёты остаются вне документации.

## Дополнение: стили, композиция и переиспользование

- [ ] У каждой визуальной части собственный SCSS-модуль и именованный класс
  на существующем корне; нет импорта SCSS родителя/соседа и лишнего DOM ради класса.
- [ ] Пустой корневой селектор проверен через сборку и реальный DOM: CSS Modules
  не гарантирует сохранение пустого правила. Нет фиктивных деклараций.
- [ ] Выделенные подкомпоненты имеют именованные папки; фрагменты JSX не дробятся.
- [ ] Интерактивная панель возле якоря (например, InputCalendar или Select) использует
  Dropdown через подходящий контракт и не копирует portal/position/dismiss. Tooltip
  и Modal сохраняют собственные семантику и lifecycle, переиспользуя нужное общее ядро.
- [ ] InputCalendar сохраняет собственные правила выбора/валидации даты;
  Dropdown владеет поверхностью, позиционированием, порталами и dismiss.
- [ ] На этапе DelbaUI изменения принадлежат её репозиторию. Обновление сайта, CMS
  и их ссылок выполняется отдельным согласованным этапом интеграции. Playwright выполняется после завершения
  всех групп изменений, затем исправления и повтор затронутых сценариев.
