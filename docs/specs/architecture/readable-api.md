# Читаемый UI API и внутренние механизмы

Статус: согласованные требования владельца, 2026-11-02. Область: только DelbaUI.
Общий рефакторинг всей библиотеки разрешён; неподтверждённые новые публичные сигнатуры
не считаются существующим API. Текущие
exports и договоры сверяются с исходниками и каталогом компонентов.

## Уровни ответственности

### Ориентир единой системы компонентов

Статус: ориентир, согласованный владельцем для дальнейшего проектирования.
Он не объявляет предлагаемые hooks/exports существующими. Владелец отдельно
разрешил реализацию Input по согласованному дереву и единому FieldPolicy,
а затем самостоятельного Calendar и его именованных подкомпонентов;
теперь владелец разрешил последовательный рефакторинг всей DelbaUI; сайт и CMS исключены.

Направление: Core предоставляет небольшие общие возможности; модель компонента
описывает сценарий через их типизированные двери; React-компонент собирает
представление; проектный D-компонент задаёт skin/size/preset. Один механизм имеет
одного владельца состояния, записи, событий и cleanup. Политика конкретного
компонента остаётся у его модели. Общие фокус и popup не включают правила выбора
товара, открытия конкретного Select или отображения конкретного плеера.

Иллюстративные двери: `field.value.set`, `field.validation.check`,
`focus.request/contains/active`, `select.selection.set`, `modal.visibility.close`,
`player.playback.play`. Это словарь назначения, не действующие сигнатуры.
React hook создаётся обычным use-именем с проверкой rules-of-hooks. Предложенный
useFocusScope должен учитывать несколько областей/порталов, ownerDocument,
замену ref target, unmount, начальный фокус и композицию пользовательских событий;
показанный в обсуждении короткий эскиз не подтверждает все эти свойства.

Предварительная анатомия: Component.tsx, Component.model.ts, Component.config.ts,
Component.types.ts, Component.module.scss, index.ts. Это предложение для проверки
на настоящем компоненте, не уже обязательные шесть файлов для всех примитивов.
Небольшие внутренние виды хранятся рядом. Крупный самостоятельный подкомпонент
получает папку Name/Name.tsx, где может иметь собственный SCSS/config; общая папка
parts вместо именованных папок не применяется. Фрагмент на 1–10 строк обычно
остаётся прямо в JSX, если не требует самостоятельного договора. Общий компонент не переносится в core
вместе с JSX: core владеет механизмами, components — представлением.

Реализуемость подтверждается работающим примером и сохранением сценариев, а не
искусственным type stub отсутствующего ядра. Input и Calendar задают принятый ориентир;
остальные компоненты проходят тот же полный путь проверки с реальными потребителями. Оптимизация не объявляется без измерения.

Перед реализацией группы фиксируются дерево, владельцы механизмов и существенные
интерфейсы. Финальная проверка сопоставляет фактические файлы с принятым эталоном.
Автономная работа разрешена в этих границах; обычные внутренние решения принимаются
самостоятельно. Изменение согласованной композиции или публичного поведения нельзя скрывать. Согласованные
композиции не заменяются молча новыми версиями. Количество файлов/строк считается
для всего пути, включая добавленные Field/Core/общие компоненты; уменьшение одной
папки за счёт вынесенного большого controller не доказывает упрощение.

Потребитель выражает намерение через публичный компонент или типизированный
controller. Компонент соединяет состояние и представление. Общий механизм
владеет lifecycle, событиями и ресурсами. Ядро реализует алгоритм и работу с DOM.
Чем выше уровень, тем меньше технических подробностей требуется потребителю.
Низкий уровень допускает необходимую алгоритмическую сложность, но не смешение
несвязанных обязанностей, неясные имена или дублирование общего механизма.

Короткий вызов не завершает инкапсуляцию. За ним проверяются все реализации до
ядра: перенос большого обработчика в helper не считается упрощением. Новая
граница имеет самостоятельный договор, уменьшает связность и число зависимостей.
Обычные if/for/Map и свойства не получают сервисные обёртки ради точек.

UI не содержит корзину, каталог CMS или проектные словари. Он предоставляет
нейтральные компоненты, команды, настройки и подписки. Проект может собрать
свою предметную дверь, используя UI, без копирования его механики.

## Публичные входы и команды

Импорты идут из exports пакета, одна декларация на один вход. Не вводи корень
`ui.*` для каждого JSX-компонента или утилиты. Существующие `Flex`, `Grid`,
`Text`, `Button` остаются понятными публичными именами. Предметная иерархия
полезна у controller, если раскрывает состояние и команды конкретного механизма.

Hover показывает назначение, параметры, результат, эффекты, отказ и среду.
Команда действует при вызове, подписка обеспечивает реактивное чтение. Не
меняй команду на фабрику обработчика ради `onClick={command(id)}`:
`onClick={() => command(id)}` сохраняет честный договор.

React-хуки имеют use-имена, явное место создания и одного владельца состояния.
Если публичная композиция использует namespaced hook, её допустимость проверяется
настоящим lint/compiler потребителя. Не ослабляй правила ради синтаксиса.
У установленного потребителем `eslint-plugin-react-hooks@5.0.0` глубоко вложенный
`site.product.usePage()` не распознаётся `rules-of-hooks`; согласованное имя
не считается проверенным API до решения этой статической проверки.
Контекст, DOM ref, controlled value и imperative handle сохраняют разные роли.

## Однократное подключение и уведомления

Общая механика подключается один раз в layout/конфигурации. Потребитель не пишет
вторую одноимённую команду ради UI-реакции и не воспроизводит алгоритм библиотеки.
Настройка может привязать действия к экземпляру; экземпляры и подписки имеют
однозначные mount/unmount и границы документа.

Согласованное направление уведомлений — публичный импорт `toast` и методы
`toast.success(message)` / `toast.error(message)` при однократном ToastProvider.
Сейчас DelbaUI предоставляет `ToastProvider` и `useToast().show(options)`;
прямой `toast` ещё не является существующим export. Точный договор реализации,
включая вызов до mount, несколько providers и несколько документов, требует
отдельного согласования. Безадресная рассылка всем providers недопустима.

Layout не создаёт глобальную переменную JavaScript: функция импортируется явно.
Серверный запрос не пишет в process-global очередь пользовательских уведомлений.
Результат команды остаётся достоверным, даже если UI-реакция дала сбой.
Ошибка поля остаётся у поля; уведомление не заменяет её и не обещает доставку
письма или успешную оплату вместо подтверждённого результата.

## Настройки и единообразие

Сообщения общей UI-валидации имеют единый типизированный словарь настроек;
отдельное поле может явно переопределить сообщение. Строка required не зашивается
в реализации каждого поля. Согласована возможность будущих переводов, но текущая
задача Input не включает выбор языка, locale provider, загрузку переводов или
реактивное переключение локали. Пример locales — направление будущего договора,
а не требование внедрить сейчас всю систему локализации.

Общий вход конфигурации собирает модульные определения. Реестры поддерживаемых
возможностей — источники типов и проверки полноты; второй список не поддерживается.
Геометрия выражается штатными props; skins/presets задают повторяемое оформление,
SCSS обслуживает правила, которые действительно требуют CSS. Новые типографические
варианты не добавляются ради обхода существующей темы.

Пятифайловая анатомия публичных проектных D-компонентов не навязывается каждой
внутренней функции или примитиву UI. Проверяй реальную ответственность, а не
симметрию папок. Удаление лишней обёртки сохраняет контракт потребителей.

## Анатомия компонента и внутренние двери

Компоненты следуют общей системе обязанностей. Это договор устройства, а не
требование создать одинаковое число папок для любого примитива:

| Область | Ответственность | Что ей не принадлежит |
| --- | --- | --- |
| Композиция | Читаемая сборка частей через их интерфейсы | Формулы маски, управление кареткой, цепочки обработчиков |
| Представление | Подпись, control, действия, feedback, дополнительные поверхности | Проверка значения и отдельная копия его состояния |
| Оформление | Разрешение props, размеров, состояний и повторяемых пресетов | Ввод, валидация, бизнес-данные потребителя |
| Модель | Значение и переходы его состояния, договор команд | JSX и универсальный мешок всех refs/flags компонента |
| Взаимодействия | Сценарии focus, blur, change, клавиатуры; композиция внешних callbacks | Реализация всех алгоритмов всех режимов в одном обработчике |
| Режимы | Особенности text, phone, number, time, date у своего владельца | Динамический вызов React-хуков из реестра |
| Проверки | Правила валидности, момент проверки и результат | Самостоятельный рендер ошибки и копия значения |
| Ядро | Общие алгоритмы, DOM, refs, подписки и освобождение ресурсов | Тема приложения и знания о конкретном экране |

Модуль хранится у ближайшего владельца. В общий core он переносится, когда
действительно нейтрален и используется несколькими механизмами. Папка `lib`
сама по себе не объясняет архитектуру: у каждой реализации должно быть понятно,
к какой обязанности она относится. Не создавай по одному файлу на каждое событие
и не вводи универсальный framework команд ради формы дерева.

Компактность оценивается и по числу переходов между файлами. Локальные части
одного представления могут быть именованными функциями рядом; отдельный файл
не требуется для каждого заголовка, иконки, списка или небольшого адаптера.
Перед выделением назови самостоятельную причину изменения и потребителей.
Большой список flags/refs/setters не становится простым от упаковки в объект.
Повторяемая запись значения (controlled/uncontrolled, DOM, callback и результат
проверки) имеет одного владельца: специализированный режим не воспроизводит
этот протокол. Числовой режим выражает числовое преобразование и шаг, а не
повторяет все способы хранения и публикации поля.

Внутренний API имеет явное место создания и предметные разделы. Например,
`const field = useFieldModel(options)` объясняет происхождение последующих
`field.validation.check(...)` или `field.seed.restoreOnBlur(...)`. Эти имена —
иллюстрация договора, не существующие exports и не утверждённая сигнатура Input.
Короткий `validate()` без понятного владельца не заменяет архитектуру. Дверь
оправдана, когда объединяет связные правила и скрывает их механизм, сохраняя
понятными вход, результат и порядок действия. Избыточная вложенность также мешает
чтению: глубина определяется предметом, а не требуемым количеством точек.

Согласованная композиция служит эталоном реализации. Нельзя молча заменять
её другой схемой или непрозрачным spread большого объекта. При обнаружении
препятствия сначала покажи конкретную несовместимость и согласуй изменение.
Перед реализацией показывается законченный путь, включая внутренние модули;
два коротких внешних файла не подтверждают качество остальной реализации.

## Обязательный чеклист

До проектирования и перед показом результата:

- [ ] Прочитан весь компонент, его внутренние зависимости и настоящий потребитель;
  новая форма API отделена от существующего кода.
- [ ] У каждой операции назван владелец. Потребитель не копирует общую механику,
  новая обёртка не просто переименовывает вызов.
- [ ] До добавления обёртки или локального состояния проверены возможности
  используемого примитива. Например, Text.collapse уже удерживает текст на время
  закрытия: дополнительный Flex.collapse и локальная копия текста не нужны.
  Проверены зазоры в пустом, открытом и закрывающемся состоянии.
- [ ] Полный путь API → controller/hook → ядро → DOM выражает последовательные
  обязанности; старый сложный обработчик не просто перенесён в другой файл.
- [ ] Реализация сопоставлена с согласованной композицией; её интерфейсы не
  заменены без обсуждения. У каждого внутреннего раздела понятны происхождение,
  ответственность и короткий договор; нет общего мешка всех flags/refs/callbacks.
- [ ] Зафиксирован конкретный эталон будущих файлов и дерева до реализации.
  После реализации проверено соответствие каждого файла; отклонения не скрыты.
  Показаны также новые общие зависимости, их ответственность и реальный размер.
- [ ] Раздельно проверены представление, оформление, модель, взаимодействия,
  режимы, валидация и ядро. Новые границы уменьшают зависимость между ними,
  а не только длину файлов. Неизменённые внутренности также прочитаны.
- [ ] Экспорт и JSDoc дают точные подсказки. Команда, snapshot и подписка различимы;
  props не требуют знания внутренних формул или ручной сборки lifecycle.
- [ ] Механизм и UI-реакция выполняются один раз; конфигурация имеет один вход,
  типы и возможности происходят из реальных реестров.
- [ ] Артефакты конфигурации принадлежат приложению: проверен сценарий двух
  приложений с одной физической копией пакета. Генератор, runtime и checker
  одинаково понимают поддерживаемые значения; их договоры не расходятся.
- [ ] Нет второго владельца состояния, stale callback, обратных импортов, утечки
  подписок/таймеров или разделения серверного состояния между пользователями.
- [ ] Тип команды соответствует фактическому sync/async-результату; ожидание
  ещё не смонтированного controller имеет определённые отмену и срок жизни.
- [ ] Сохранены DOM/ref, композиция событий, отмена, SSR/hydration, несколько
  документов, клавиатура, фокус, нативный form/reset и reduced motion по сценарию.
- [ ] Предложение уменьшает связность; много передаваемых refs/callbacks не
  замаскированы новым hook. Число строк не служит доказательством качества.
- [ ] Проверено всё дерево файлов: нет микрофайлов без самостоятельной
  ответственности и переименовывающих адаптеров. Число файлов и переходов
  сопоставлено с прежним устройством; увеличение объясняется обязанностями.
- [ ] В разных режимах не повторяется протокол записи значения и уведомления.
  Потребитель общего механизма не знает, как хранится controlled/uncontrolled
  значение; дверь не является просто новым мешком прежних setters/callbacks.
- [ ] Проверены consumers и переход публичного API; неиспользование одним сайтом
  не оправдывает удаление библиотечного export.
- [ ] Явно указаны просмотренное, предложенное, выполненное и непроверенное.
  Кодовые/браузерные проверки выбраны по фактическому diff.

## Полный аудит и согласование

Инвентарь строится из всех исходников: components, core, hooks, skin, тема,
публичные входы, генерация и проверки. Для каждой области отмечаются полное,
частичное чтение и непрочитанное. Большой файл — повод изучить связность, но
не самостоятельное доказательство проблемы. Для каждого вывода нужны точный
исходник, цепочка исполнения, потребитель, предлагаемая граница и критерий проверки.

Предыдущий вариант [Input](../ui/components/Input.md) был отклонён владельцем.
Новый договор утверждён: один Field engine, чистые политики режимов и явная
композиция Input с деревом на странице компонента. Реализация разрешена для всей DelbaUI по отдельным группам компонентов. Приёмка должна проверить внутренности и сохранение поведения.
Сайт и CMS не редактируются, ссылки сабмодулей у них не обновляются. Совместимость
проверяется по реальным вызовам и типам; их глобальная миграция не включена.
Отчёты аудита остаются в обсуждении или вне репозитория; здесь хранятся устойчивые
требования. Проверки — [приёмка](../verification/acceptance.md), текущие API —
[каталог компонентов](../ui/components/README.md).

## Собственные стили и узнаваемый DOM

Согласованное требование владельца: каждый визуальный компонент и выделенный
подкомпонент имеет собственный Name.module.scss. Его существующий корневой
DOM-узел получает className с styles.Name, например styles.CalendarDays.
Не добавляй обёртку только ради класса. Портальные поверхности также получают
собственный именованный класс. Hooks, providers без DOM и чистые функции не
получают искусственную разметку или SCSS.

Подкомпонент не импортирует SCSS родителя или соседа. Собственные селекторы
переносятся в его модуль; общие токены и SCSS-миксины берутся из ядра.
Геометрия остаётся в поддерживаемых layout-пропсах. Собственный корневой
селектор обязателен даже без деклараций; не добавляй фиктивные стили ради
сохранения класса. Проверяй сборкой, что пустой селектор действительно
экспортируется и имя остаётся в DOM; если сборщик удаляет его, обеспечь
явный стабильный маркер Name через общий договор классов, а не фиктивную CSS-декларацию.
CSS Modules могут добавлять хеш к имени; назначение Name должно оставаться узнаваемым.

Самостоятельная часть располагается в Name/Name.tsx и Name/Name.module.scss
внутри владельца. Для Input это касается InputControl, InputActions,
InputCalendar и InputOverflow. Чистые модели, политики и форматы остаются
модулями логики. Фрагменты без самостоятельной ответственности остаются в JSX.

Это целевое правило миграции всей DelbaUI, а не утверждение о соответствии
текущего кода. Существующие ui-* классы сохраняют договор генерации и темы;
именованные классы компонентов дополняют их без второго владельца стилей.
