# Разработка Frontend

Перед изменением прочитай [архитектуру](architecture.md), профиль из
[AGENTS.md](../AGENTS.md) и типы публичного входа. Потребитель согласовывает
предметные требования отдельно. Изменение общей механики учитывает разных
потребителей. Изменение публичного договора включает миграцию вызовов
и обновление [каталога](components.md).

## Публичный компонент

Новый публичный примитив и новый проектный D-компонент оформляются одинаково.
При миграции существующего компонента приводи его к этой структуре.

```text
Name/
├─ Name.tsx
├─ Name.types.ts
├─ Name.config.ts
├─ Name.module.scss
└─ index.ts
```

- `Name.tsx` показывает композицию, связь props с DOM и действия компонента.
- `Name.types.ts` описывает публичные props и документирует их смысл.
- `Name.config.ts` хранит defaults, размеры, пресеты, skins и states по мере
  необходимости. Для D-компонента это единственный локальный config.
- `Name.module.scss` хранит собственные стили по [договору композиции](architecture.md#композиция-и-оформление).
- `index.ts` явно определяет публичные экспорты папки.

Все пять файлов обязательны. Файл без собственной ответственности может быть
пустым. Модель, hooks, helpers и подчасти
выделяй по реальной ответственности. Внутренним частям достаточно структуры,
которая нужна их владельцу. Публичный prop сохраняет TS, DOM и accessible
контракт одновременно, включая refs, handlers, focus, SSR и reduced motion.

Имя каждого файла соответствует фактическому имени компонента. Папка
`RichText` содержит файлы `LexicalText.*`, папка `RichTextarea` —
`LexicalTextarea.*`. Публичные составные части, например Accordion.Item,
имеют свой набор файлов и экспортируются через владельца.

Текущий пакет применяет этот договор ко всем публичным компонентам Frontend.
Общие интеракции, состояние и эффекты используют механизмы ядра там, где
позволяет настоящий DOM. Точки входа и примеры есть в [каталоге](components.md).

## Тестовые исходники и контур

Весь тестовый исходник, включая tools и type-test, хранится в корне
`tests/<Domain>/unit` или `tests/<Domain>/integration`. Домен называй по
владельцу поведения. Fixture рядом с набором тестов. Домен `Tools` владеет
тестами генерации, правил и команд, исходники команд остаются в `tools/`.
Type tests входят в свой домен, runtime discovery их не исполняет.

Frontend использует Next и React. Проверки библиотеки работают с полным
`starterFrontend`; приложение запускает свой runner с собственным config.
Generated source checkout принадлежит активному config. Проверки с разными
settings выполняются последовательно, после смены контекста подготавливаются
нужные проекции. Правила проверок не создают baseline. См. [конфиг](configuration.md).

После разрешения `pnpm --filter @delba/frontend check` запускает library gate.
Скрипты `test`, `typecheck` и `boundary` дают более узкий охват.
Команды `delba frontend check` и `delba frontend test` получают settings
из Toolkit; `check` проверяет потребителя, тесты приложения принадлежат его модулю.
`@delba/frontend/verify` предоставляет runNode/runNodeTests/runSteps для явных
адаптеров. Аргументы и объём бери из [package.json](../package.json) и
[module actions](../tools/module.mjs).

## Приёмка

Текущий согласованный пакет SOURCE ONLY в существующей `work/refactor`.
Разрешены исходники, дифф и исходники тестов. Запуски tests, lint, types,
build, браузера, native/DB, validators и CLI gates ждут отдельного разрешения.
Сохраняй чужой diff. Новые изменения остаются в Changes. Source review и
наличие generated files не подтверждают выполненный runtime check.
При чтении исходников сверяй пять файлов, импорты и тип каждого объявленного
эффекта с его фактическим подключением к DOM.
Тот же порядок приёмки действует для общих календаря, выбора и прокрутки.
Сверяй клавиатуру, повторный выбор даты, смену scope при отметках, частичный
отказ записи и независимость прокрутки окна и контейнеров.

После разрешения закончи независимый пакет и выбери адресные проверки.
Общая проверка зависит от готовности стыков. Для UI проверь сборку и доставку
CSS в Next, viewport и реальные экраны разных потребителей. Ручная приёмка
включает реальный ввод, клавиатуру, фокус, клики, скролл, порталы, длинные/пустые
данные и изменённые состояния. Для замеров используй одинаковые сборку,
viewport, данные и состояние. Для запуска и ручной проверки применяй общие
delba-launcher и delba-browser. Playwright и отдельный Vite browser harness
исключены из контура.

delba-verify задаёт общий порядок. Исправляй причины и повторяй упавшие
и затронутые проверки. Сохраняй проверяемый договор у владельца, результаты запуска —
во внешнем delba-plan. История прежней документации доступна в Git.
