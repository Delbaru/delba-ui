# Оснастка: генератор, сабмодуль, скрипты

### Общий marker guard проверяет потребителей без автоматического baseline

Anatomy-check ограничен src/components кита и не защищал CMS/project className.
Теперь один AST-владелец в project-props используется anatomy и check-rules:
он следует за локальными class-значениями, массивами и template fallback, сохраняя
utility/vendor/module контракты. Walker читает также runtime-модели TS/JS;
одиночный TypeScript checker использует allowJs для привязок локальных JS-переменных.
Старый CLI автоматически принимал текущие нарушения нового правила в baseline;
для global-component-class разрешён только ноль. CLI-регрессия проверяет отсутствие
ключа, искусственно завышенную планку и отказ --update записать нарушения.
Native range owner тоже распознаётся по настоящей привязке собственного CSS-модуля:
старый поиск literal Range ложно запрещал штатный DRange после очистки. Регрессия
сохраняет annotation/type/form-contract проверки и отвергает подмену styles параметром.

### Скорость жеста не задаётся числом mouse.move steps

Четыре движения Playwright под нагрузкой занимали разное время: release velocity
могла стать ниже порога инерции, хотя тест требовал дополнительное продвижение.
Для отдельного velocity-contract regression используется trusted CDP mouse stream
с одинаковыми явными timestamps для baseline, inertia и reduced motion. Во время
mouseMoved сохраняются button:left и buttons:1, иначе браузер теряет pointer capture.
Проверки остальных drag-сценариев остаются настоящими page.mouse действиями;
ожидания расстояния и reduced motion не ослаблены.

### Команда проверки потребителя определяется его scripts

**Симптом.** В ui-verify было указано `npm run ui:test --silent` «из корня сайта»,
но в GrigorevPrint ни корневой, ни прикладной package.json не содержат `ui:test`.

**Причина.** Обёртка запуска одного потребителя была описана как общий договор библиотеки.

**Исправление.** Навык указывает прямой `pnpm exec delba-ui test` из каталога приложения
с ui.config; корневые aliases и включение gate в `verify` проверяются по конкретному проекту.

**Повторная проверка.** Прочитать scripts корня и приложения, подтвердить наличие ui.config
и CLI-зависимости. В GrigorevPrint подтверждены `apps/site/ui.config.ts` и `@delba/ui`
в dependencies приложения; `verify` корня включает check/build, а не отдельный `ui:test`.
Это проверка корректности инструкции, не выполненный продуктовый gate.

### Новое значение пропа без генератора — молча мёртвый класс

Классы утилит печатаются под значения, которые генератор НАШЁЛ в коде проекта. Появилось новое
число или цвет — без прогона генератора (`npm run ui:build` в socrat) класс на узле есть, а правила
под него нет. В DevTools это выглядит как «стиль не применился».

**Правило: после правки, добавляющей значение пропа, генератор гоняется обязательно.** Проверка —
проба мёртвых классов, а не оракул стилей: мёртвый класс оракул видит только следствием.

### Правка библиотеки из проекта — это коммит СЮДА

Папка библиотеки внутри проекта — отдельный репозиторий. Порядок: в ней `git switch main` → правка →
коммит и пуш здесь → в проекте `git add <путь>` и коммит сдвига указателя. Иначе проект хранит
ссылку на коммит, которого ни у кого нет.

**История этого репозитория не переписывается.** Проекты закреплены на конкретных коммитах.

### Чужая правка библиотеки, сделанная ДО выноса, переносится патчем

Коллега правил `UI/` в проекте, когда та ещё была обычной папкой. `git merge` такое не берёт:
по этим путям у проекта теперь сабмодуль, и git отказывается писать поверх его файлов
(«untracked working tree files would be overwritten»).

**Рецепт:** снять их правки патчем (`git diff <база> <их main> -- <путь до UI>`), применить в
репозитории библиотеки со срезанным префиксом (`git apply -p7`), закоммитить и запушить ЗДЕСЬ; в
проекте слить их работу без папки UI и подвинуть указатель. Куски, которые не встали (файл успел
измениться), сводятся руками — их у нас был один из восьми.

### `| head` гасит фоновый процесс, а `&&` после конвейера врёт про успех

`npm run dev:app | head -40` в фоне поднимает сервер и тут же его убивает: `head` закрывает
конвейер. А `nx build … | tail -25 && echo OK` печатает «OK» даже когда сборка упала: код возврата
берётся от `tail`.

**Правило: долгоживущую команду запускаем без конвейера, а успех проверяем по тексту вывода
сборки, а не по коду возврата конвейера.**

### Разметку `Img` без запущенного Next не отрисовать с первого раза — три ловушки

Проверяли, что `Img` с кортежем `src` собирает `<picture>`: `renderToStaticMarkup` из
временного скрипта (`node --import tsx`) вне проекта. Упало трижды подряд:

1. `Invalid hook call` — `react-dom/server` подтянулся из чужой папки (`~/node_modules`), а

   проекта-потребителя.
2. `React is not defined` — файлы библиотеки tsx собирает классическим JSX (`tsconfig`

3. `hostname … is not configured under images` — вне Next нет `next.config` с
   `remotePatterns`. Лечение — локальные пути (`/media/hero.jpg`) в проверке.

**Правило: проверка разметки компонента на `next/image` вне Next — один React явными путями
проекта, `globalThis.React` и локальные адреса картинок. Иначе проверяешь окружение, а не
компонент.**

### `.ts` проекта грузится как CommonJS мимо ESM-хука tsx — «Cannot find module» при живом файле

CLI кита звал `register()` из `tsx/esm/api` и импортировал `ui.config.ts` проекта. Упало
`Cannot find module './src/shared/ui/core/axes'` с `Require stack`: у проекта нет `"type": "module"`,
и Node (22.18+/24) грузит `.ts` сам — как CommonJS, со срезанием типов, но без подбора расширений.
ESM-хук tsx до `require` не доходит.

**Лечение:** регистрировать оба хука — `tsx/cjs/api` и `tsx/esm/api`. Default-экспорт такого
модуля при `import()` лежит на уровень глубже (`mod.default.default`), именованные — и поимённо,
и в `default`. Граф модулей для перезапуска watch — `onImport` ESM-хука плюс `require.cache`.

### Watcher из `next.config` — ребёнок того процесса, который грузит конфиг, и умирает по IPC

`next dev` грузит конфиг не в CLI-процессе, а в дочернем сервере (`start-server`), и тот может
перезапускаться. Watcher, порождённый из конфига без связи с родителем, на Windows остаётся
сиротой: Ctrl+C и `taskkill` без `/T` до внуков не доходят.

**Правило:** запускать watcher с IPC-каналом (`stdio: [..., 'ipc']`) и выходить по `disconnect` —
канал рвётся при любой смерти родителя, включая `taskkill /F`. `unref()` ребёнка и канала — чтобы
watcher не держал dev живым. От повторного запуска в других процессах Next — метка в `process.env`
(дочерние процессы её наследуют). Проверено: `taskkill /F` одного сервера Next снимает watcher,
порт свободен.

### SCSS кита через `exports` пакета — потерянные относительные `@use`

Симптом: `@use '@delba/ui/styles'` с `exports["./styles"]` → `Can't find stylesheet to import`
на `meta.load-css('./scale')` внутри `tokens.global.scss`; `@use '@delba/ui/skin'` при JS-входе `./skin`
отдавал sass файл `index.ts` («expected "{"»). Причина: bare-имя резолвит импортёр sass-loader в
Turbopack — по `exports`, через симлинк `node_modules/@delba/ui`, без учёта `restrictions` на `.scss`; от
файла, который он отдал, относительные `@use`/`load-css` уже не находятся. Лечение: SCSS-входы — файлы
в `tools/sass/@delba/ui/*` (`@forward` в ядро), папка — в `sassOptions.loadPaths` плагина; в `exports`
только JS; SCSS-имя не совпадает с JS-входом (`skin-states`). Проверено: вернуть `./styles` в
`exports` — сборка снова падает на `load-css`.

### Кит в `node_modules` — генератор не видит ни одного его литерала

Симптом: кит поставлен git-зависимостью (Delba CMS), `delba-ui build` проходит, а классов литералов
самого кита (`gap 8`, `r 8`, `w={[24, 24, 24]}` в его компонентах) в `_utilities.scss` нет — узлы кита

же в watch. Тест — `tools/utilities/tests/generate.test.ts`: кит под `node_modules` сканируется, `node_modules`
внутри скана пропускается.

### Анимацию в headless Playwright по времени не проверить — кадры стоят

Проверял каскад `reveal`: состояние `in`, `playState: running`, а `currentTime` держится на 0 и узел
прозрачен, пока не сработает страховочный таймер. Причина — headless-вкладка почти не рисует кадры
(6 rAF за 500 мс, первый кадр после прокрутки — секунда), а CSS-анимация стартует только с кадром.
Снимок экрана кадр даёт, но идёт 2 с.

**Лечение: ход проверяется через Web Animations, а не секундомером.** `el.getAnimations()` →
`effect.getComputedTiming()` (задержка, длительность), затем `pause()` и `currentTime = N` — и читать
`getComputedStyle` в нужных точках. «Мигает ли при загрузке» — трасса состояния и `opacity` из
`addInitScript` по rAF.

При замере плавности держи вкладку активной: фоновый rAF с интервалами около секунды
не измеряет скорость приложения. Анонимный тяжёлый `FrameRequestCallback` в trace
не приписывай компоненту по времени совпадения. На Diamonds4You такой стоп появлялся
только с записью trace; обёртка вокруг rAF страницы не находила соответствующего
тяжёлого callback. Сверяй исходник/стек и контрольный прогон без записи. Сокращение
времени одного callback также не равно улучшению полного кадра.

Промежуточные состояния двух участников фиксируй одним браузерным наблюдателем.
В fallback-тесте reveal последовательные Playwright-проверки `short=done`, затем
`long=in` иногда доходили до второй цели уже после её 600 мс хода; повторный
прогон проходил. MutationObserver, установленный до прокрутки, записывает обе
цели в одной доставке и сохраняет проверку разной scoped-длительности без гонки
между polling и концом анимации. Проверка — fallback-сценарий text-timeline,
включая переход от `{ short: done, long: in }` к обоим `done`.

### Проверка перехода на 2.0 ловила СВОЙ неймспейс проекта, а не кит

**Симптом.** `delba-ui check` в socrat печатал 45 ложных «`<Container/>` удалён» — на файлы, которые
импортируют его из `@socrat/shared/ui/components`, то есть из проекта, а не из кита.

**Причина.** `KIT_MODULE` в `tools/check-migration.mjs` стоял с флагом `i`, чтобы поймать строчный
`…/ui/container`. Но под тот же флаг попадала ветка `(^|/)(UI|delba-ui)(/|$)`, и сегмент `ui` в
ЛЮБОМ пути проекта (`@socrat/shared/ui/components`, `…/ui/hooks`) читался как папка кита.

**Лечение.** Регистр значим: папка кита — `UI` или `delba-ui`, а `/ui/container` и так записан
строчными, поэтому флаг не нужен. Соседний `DEEP` был регистрозависимым с самого начала — теперь
оба правила смотрят на путь одинаково.

**Правило: имя папки кита в регулярках — регистрозависимо.** Неймспейс потребителя может содержать
`ui` сегментом, и это не кит.

### `build` зелёный — про `watch` это не говорит НИЧЕГО: у них разный код

**Симптом.** У потребителя (socrat, 29.09.2026) `delba-ui watch` умирал в первую секунду:
`The "paths[1]" argument must be of type string. Received undefined`, надзор поднимал его заново, и
так по кругу. `delba-ui build` на том же конфиге проходил зелёным.

**Причина.** `skins.dir` объявлен НЕОБЯЗАТЕЛЬНЫМ (`UiSkins.dir?`) — проект, который печатает
состояния сам, берёт у кита только словари. Генератор шкур это честно проверяет
(`if (skins.dir === undefined) return changed`), а ветка `watch` в `cli.mjs` — нет:
`path.resolve(root, config.skins.dir)` роняло процесс. `build` до этой строки просто не доходит.

**Лечение.** Проверка в `work()`. Правило шире: **каждое необязательное поле `UiConfig` обязано
быть проверено во ВСЕХ трёх командах**, а не только там, где его читает генератор. `build`
свидетелем живости `watch` не является — гонять надо обе (`timeout 20 delba-ui watch`, в логе ноль
`✗`).

### Покадровый замер хода бьёт по закрытому блоку, а он уходит из DOM

**Симптом.** socrat, 03.10.2026, приёмка `collapse` по `docs/ui-motion-api.md` § 7: харнесс мерил
`.ui-collapse` и на прерывании возвращал «нет узла». На первом, обычном ходе всё сходилось, а на
втором — ровно там, где проверка и должна была ловить скачок.

**Причина.** Закрытый блок по умолчанию **уходит из DOM** (`collapseKeepMounted` не задан), поэтому
к концу хода обёртки, которую мерили, уже нет. Приёмка прерывания ломает узел на середине и потом
ждёт от него кадров.

**Лечение.** Меряется **карточка-владелец**: она переживает ход и теряет ровно ту же высоту. В
конструкторе это сама `StepCard` — показания совпали с прежними по обёртке (`193.3 → 46.7`, монотонно,
макс. скачок 18.5 px), а прерывание после перехода на карточку дало читаемый результат: разворот
направления ×1, макс. скачок 18.4 px.

**Правило.**

- **Покадровый замер целится в узел, который переживает ход.** Внутренний слой сворачиваемого —
  почти всегда мимо: его кладут в ноль и убирают.
- **Приёмка прерывания: критерий — только «нет скачка больше 40 px за кадр».** Монотонности там быть
  не должно по определению: ход разворачивается. Считать развороты и требовать их наличие —
  признак, что старт пошёл от текущей геометрии.
- **Картинку середины пути снимать на отдельной вкладке с `deviceScaleFactor: 3`.** На 1× полоса
  шириной в полсотни пикселей не читается, а тройной рендер роняет частоту кадров и завышает скачки
  в самих цифрах (проверено: 18 px на 1× против 36 px на 3×). Цифры снимают на 1×, картинку — на 3×.
- **Замеренный радиус проверяется на самой анимации, а не глазами.** `getComputedStyle(inner).clipPath`
  на середине хода отдал `inset(0px round 24px)`, а `--collapse-radius` на обёртке — `24px`: значит
  движок прочитал радиус с блока, а не картинка просто так круглая.

### Лог приборов в потоке страницы — и прокрутка едет сама, мимо темы теста

**Симптом.** Diamonds4You, 12.10.2026, сборка в Actions: `ui:test` падал на браузерном гейте, причём
каждый прогон на другом тесте — `Modal scroll lock allows inner wheel scrolling…`
(`Expected: 8216, Received: 8234`) и `Dropdown aligns the visible wide surface…`. Причины оказались
РАЗНЫЕ (вторая — в уроке ниже), и это стоило отдельной проверки: похожая картина падений соблазняет
склеить их в одну. Локально первый падал 6/6 — ровно на +18 px, то есть никакой это не флак.

**Причина.** Не в блокировке прокрутки, а в самой фикстуре. Корневой `<Profiler>` из
`tools/browser/main.tsx` на КАЖДЫЙ коммит React пишет растущий JSON в `<output
data-testid="react-profile">`, а тот стоял третьим ребёнком `<main class="fixture">` — в потоке, у
самого верха страницы. Каждая новая строка лога — +18 px высоты документа ВЫШЕ текущей прокрутки,
и scroll anchoring Chrome честно подкручивал `window.scrollY` на столько же, чтобы картинка не
дёрнулась. Тест снимал `pageY`, открывал модалку (это пачка коммитов), а потом сверял `scrollY`
строгим `toBe` — и ловил сдвиг от приборов, а не утечку колеса.

**Лечение.** `<output>` профайлера выведен из потока (`position: absolute`, 1×1, `overflow: hidden`):
значение по-прежнему читается из DOM, но высоту документа он не меняет. После этого 24/24 на
`-g "Modal scroll lock" --repeat-each=6` и 92/92 на всём наборе с `--workers=2 --repeat-each=2`.

**Правило.**

- **Инструментовка харнесса не стоит в потоке.** Любой `<output>`/лог, который пишется из `onRender`,
  обработчика или таймера, обязан быть вне потока или фиксированного размера. Иначе он тихо двигает
  геометрию ВСЕМ тестам на странице, а падают те, кто сверяет прокрутку и координаты.
- **«Разные тесты в разных прогонах» — повод искать общее: фикстуру, высоту документа, порядок
  коммитов.** Но общая картина не доказывает общую причину: здесь из двух падений одно было про
  фикстуру, другое — про бюджет теста. Каждое доводится до своего воспроизведения.
- **Диагностика сдвига прокрутки — замер `documentElement.scrollHeight` по шагам теста** и обход DOM
  с поиском самого глубокого узла, чья высота изменилась. Сам `scrollY` виноватого не называет: его
  двигает scroll anchoring, а растёт совсем другой узел.
- **Строгий `toBe` по `window.scrollY` держится только на странице, высота которой не меняется.**
  Если высота в принципе дышит — сравнение теряет смысл раньше, чем поймает утечку.

### Шесть ширин в одном тесте — это один бюджет на 30 с, и раннер в него не влезает

**Симптом.** Diamonds4You, 12.10.2026, Actions: `Dropdown aligns the visible wide surface…` падал с
`Test timeout of 30000ms exceeded` на `trigger.click()`, причём лог клика обрывался на безобидном
`done scrolling`. Локально тест проходил всегда — и этим сбивал с толку.

**Причина.** Не в клике. Тест гонял шесть ширин × четыре стороны = 24 цикла «открыл — померил —
закрыл» плюс шесть `page.goto` — и всё это на ОДИН тестовый бюджет Playwright (30 с по умолчанию,
в конфиге не поднят; `timeout: 30_000` там — про `webServer`, а не про тест). На рабочей машине под
двумя воркерами — 18,3 с, то есть запас всего 1,6×. Раннер GitHub медленнее, и тест умирал на том
цикле, до которого доезжал: «обрыв лога на `done scrolling`» — это просто момент, когда кончился
бюджет, а не зависший клик.

**Лечение.** Ширина стала отдельным тестом (`for (const width of …) test(`… at ${width}px`)`).
Каждая получила свой бюджет, своё имя в отчёте и считается параллельно: максимум 3,9 с вместо 18,3 с,
запас ×8. 18/18 на `--workers=2 --repeat-each=3`.

**Правило.**

- **Прогон по брейкпоинтам — это шесть тестов, а не шесть итераций.** Цикл по ширинам внутри одного
  `test()` копит время в общий бюджет, лишает параллельности и в отчёте не говорит, на какой ширине
  сломалось.
- **Запас по времени меряется, а не предполагается.** `--reporter=list` печатает длительность; меньше
  трёх-четырёхкратного запаса к бюджету — значит в CI уже красно, просто ещё не сегодня.
- **`Test timeout exceeded` называет не виноватую строку, а последнюю.** Лог, обрывающийся на
  успешном шаге вроде `done scrolling`, означает «кончился бюджет теста», а не «здесь зависло».
  Смотреть надо на суммарное время теста, а не на этот шаг.
- **Бюджет поднимать (`test.slow()`) — последнее средство.** Он прячет цену: двадцатисекундный
  монолит остаётся монолитом. Сначала режется на части, которые считаются параллельно.

### Исчезнувший путь из файлового снимка не должен ронять watch-генерацию

**Симптом.** CMS dev остановился во время легитимного case-only Git rename: `walk` успел

**Причина.** Снимок имён и чтение исходников — отдельные операции файловой системы; watcher

**Исправление.** При чтении источника пропускать только `ENOENT`, удалять его запись из кеша и
продолжать текущую генерацию. Ошибки доступа, чтения и остальные I/O ошибки должны подниматься.

**Проверка.** `tools/utilities/tests/generate.test.ts` удаляет файл после `walk`, проверяет
пропуск и очистку кеша, а также подтверждает, что `EISDIR` не подавляется.

### Восстановление исходников использует проверенный снимок — 2026-10-27

**Причина.** Массовый plain Prettier
внёс постороннее форматирование в пять файлов. Попытка вернуть оформление через
offset-ы JS scanner и Python string повредила исходники: Windows text-mode subprocess

Проверка — восстановленный baseline, TypeScript и те же browser regressions.
При таком восстановлении нужен проверенный исходный снимок; переносить scanner offsets
между языками и представлениями текста нельзя.

### Успешный HTTP не подтверждает принадлежность браузерного стенда

### Условие и ключ lookup не передают своё содержимое в CSS

**Симптом.** Генератор утилит напечатал `color: UI review.stl` из бизнес-поля
`parts[].name`, после чего Sass не смог разобрать stylesheet.

**Причина.** Анализ проброса считал `error ? 'error' : 'muted'` передачей текста
ошибки в `tone`, а `tones[tone]` — передачей самого ключа в `color`. Общая карта
источников затем связала любое поле `name` с цветом через `errors.name`.

**Лечение и проверка.** В provenance тернарника обходи возвращаемые ветки,
у `&&` — правую часть, у индексированного доступа — объект значений, а не ключ.
Не фильтруй допустимый CSS вместо исправления ложного маршрута. Regression в
`tools/utilities/tests/extract.test.ts` проверяет текст ошибки, имя STL и lookup/guard,
сохраняя извлечение настоящих цветов. После изменения tools перезапусти процесс
генератора: существующий watcher не перечитывает собственный код.

### Перенос тестов сохраняет разрешение файлов и проверку типов

**Причина.** При переносе unit/static/browser тестов в `tests/` одной правки

## Собственные SCSS в unit/SSR-проверках

Node unit-runtime явно обрабатывает существующие SCSS/CSS как пустые exports,
